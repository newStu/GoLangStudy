# 参数绑定与校验：ShouldBindJSON 背后的两层机制

> 本篇对应 `handler/auth_handler.go`，拆解 `c.ShouldBindJSON(&req)` 这一行背后的机制：Gin 负责"绑定"，validator 负责"校验"，两者是配合关系。

## 一、问题：`ShouldBindJSON` 自带参数校验吗？

答案是**一半一半**。`binding:"required"` 和 `ShouldBindJSON` 看起来像一体的，实际是两层各自独立的机制：

| 层 | 谁做的 | 作用 |
|---|---|---|
| JSON 解析 + 字段填充 | Gin 自带（`ShouldBindJSON`） | 把请求 Body 反序列化到结构体（绑定） |
| 规则校验（`required` 等） | Gin 内置集成的 `go-playground/validator` v10 | 检查字段是否满足 `binding` tag 里的规则（校验） |

## 二、绑定层：ShouldBindJSON 只做"翻译"

`c.ShouldBindJSON(&req)` 的本职工作是：

1. 读取请求 Body（`c.Request.Body`）
2. 用标准库 `encoding/json` 反序列化，按 `json:"username"` tag 把 JSON 字段填到结构体上
3. 绑定完成后，**顺带**调用 validator 扫描 `binding` tag 执行校验（见下一节）

只做绑定的话，只有 JSON 本身格式错了（发的不是 JSON 文本、字段类型对不上）它才报错。`username` 传成空字符串它不管——那是校验层的事。

## 三、校验层：validator 库

真正让"缺字段返回 400"生效的是结构体 tag：

```go
type loginRequest struct {
	Username string `json:"username" binding:"required"`
	Password string `json:"password" binding:"required"`
}
```

- `binding:"required"` 是写给 **validator** 看的规则，Gin 没有自己从零写校验逻辑，而是内置集成了第三方库 `go-playground/validator`（v10）。
- 这个依赖不是我们直接 `go get` 的，是跟着 `gin-gonic/gin` **间接**进来的。验证方式：

```bash
go mod graph | grep validator
# github.com/gin-gonic/gin github.com/go-playground/validator/v10@v10.x.x
```

- 任何一条规则不满足，`ShouldBindJSON` 就返回 `err`，于是走到 400 分支：

```go
if err := c.ShouldBindJSON(&req); err != nil {
	common.Fail(c, http.StatusBadRequest, "参数错误：username 和 password 必填")
	return
}
```

### 3.1 常用校验规则

`required` 只是众多规则里最简单的一个，规则可以逗号组合：

| 规则 | 含义 | 示例 |
|---|---|---|
| `required` | 零值也算缺（`""`、`0`、`false` 都不通过） | `binding:"required"` |
| `min` / `max` | 字符串按长度、数字按大小 | `binding:"min=6,max=20"` |
| `email` | 邮箱格式 | `binding:"required,email"` |
| `oneof` | 枚举值 | `binding:"oneof=male female"` |
| `gte` / `lte` | 数字比较（常配合范围） | `binding:"required,gte=1,lte=100"` |

试一下组合规则——把 `Password` 的 tag 改成：

```go
Password string `json:"password" binding:"required,min=6"`
```

然后发一个 3 位密码的请求，就会得到 400，而不是等到 service 层比对 bcrypt 才失败。**能在入口拦住的非法参数，不要放进业务层**。

### 3.2 错误信息里有什么

`err` 的具体类型是 `validator.ValidationErrors`（一个切片，每个失败字段一条），原始信息类似：

```
Key: 'loginRequest.Password' Error:Field validation for 'Password' failed on the 'min' tag
```

直接把它返回给用户体验很差（英文、暴露内部字段名），所以 handler 里写死了人话："参数错误：username 和 password 必填"。实际项目常见的做法是遍历 `ValidationErrors`，按"字段 + 规则"映射成中文提示，不过学习阶段先保持简单。

## 四、Bind 家族方法对比

| 方法 | Content-Type | 校验失败时 |
|---|---|---|
| `ShouldBindJSON` | 只管 JSON | 返回 error，**由自己决定响应**（本项目用它） |
| `BindJSON` | 只管 JSON | 自动写 400 响应，不好定制错误消息 |
| `ShouldBind` | 按请求头自动选（JSON/form 等） | 返回 error |

约定：**用 `Should*` 系列**，错误处理握在自己手里，才能配合统一响应格式 `common.Fail(c, ...)` 输出。

## 五、小结

- `ShouldBindJSON` = JSON 反序列化（Gin）+ tag 规则校验（validator），一行完成绑定和校验。
- `json:` tag 管字段名映射（绑定），`binding:` tag 管规则（校验），两套 tag 各管一头——和 GORM model 上 `gorm:` / `json:` 双 tag 是同一个思路。
- 规则组合写在 `binding:"..."` 里，逗号分隔；非法参数在 handler 入口拦掉，不进业务层。
