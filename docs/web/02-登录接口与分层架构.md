# 登录接口与分层架构

> 本篇对应 `config/`、`database/`、`model/`、`dao/`、`service/`、`handler/`、`common/`、`scripts/init.sql`，记录从"占位路由"到一个真实可用的 login 接口的完整过程：接入 MySQL、按实际项目标准分层、密码校验与统一响应。

## 一、为什么要分层

之前的路由是这样写的：`auth.POST("/login", func(c *gin.Context) { c.JSON(...) })`，逻辑直接写在路由注册处。接口一多，所有代码挤在 `router/` 包里没法维护。实际项目通常按下图分层，一次请求的流转路径：

```
HTTP 请求
   │
   ▼
router（路由注册，只做"哪个路径调哪个 handler"的映射）
   │
   ▼
handler（解析请求参数、参数校验、调 service、按结果写响应）
   │
   ▼
service（业务逻辑：登录=查用户+比对密码，定义业务错误）
   │
   ▼
dao（数据访问：只管怎么查库，不管业务含义）
   │
   ▼
model + database（表结构定义 + 连接）
```

每层的职责边界：

| 层 | 职责 | 不该做的事 |
|---|---|---|
| handler | 参数绑定校验、调 service、组装 HTTP 响应 | 不写业务判断、不碰数据库 |
| service | 业务规则、业务错误定义 | 不解析 JSON、不拼 SQL |
| dao | 增删改查 | 不理解业务语义（查不到就返回 `ErrRecordNotFound`，"这意味着登录失败"是 service 的解读） |

好处：换 HTTP 框架只动 handler；写单元测试时 service 可以 mock 掉 dao；SQL 全部集中在 dao 层。

## 二、接入 MySQL（GORM）

### 2.1 连接配置：config/config.go

```go
const MySQLDSN = "golang:golang123456@tcp(127.0.0.1:3306)/golang_study?charset=utf8mb4&parseTime=True&loc=Local"
```

DSN（Data Source Name）格式：`用户名:密码@tcp(地址:端口)/库名?参数`。几个要点：

- **密码里含 `@` 等特殊字符时要 URL 编码**（`@` → `%40`），否则解析器会把 `@` 后面当成主机地址。
- `parseTime=True` 让 MySQL 的 `DATETIME` 自动扫描成 Go 的 `time.Time`，不加的话读到的是 `[]byte`。
- 实际项目不会把密码写死在代码里（会进 git），通常用配置文件或环境变量；学习阶段先这样，但**账号权限要收敛**——见下面 2.4。
- 本机 MySQL 跑在 Docker 容器里（`opinion-mysql`，5.7），宿主机连 `127.0.0.1:3306` 即可。

### 2.2 初始化连接：database/db.go

```go
var DB *gorm.DB

func InitDB() {
	db, err := gorm.Open(mysql.Open(config.MySQLDSN), &gorm.Config{})
	if err != nil {
		log.Fatal("连接 MySQL 失败: ", err)
	}
	sqlDB, _ := db.DB()
	sqlDB.SetMaxIdleConns(10)
	sqlDB.SetMaxOpenConns(100)
	sqlDB.SetConnMaxLifetime(time.Hour)
	DB = db
}
```

- `gorm.Open` 返回的 `*gorm.DB` 是连接池的抽象，底层真正的 `*sql.DB` 通过 `db.DB()` 拿到，用于设置连接池三个参数。
- 全局变量 `DB` 最直观；生产项目更常见**依赖注入**（main 里创建后逐层传给 dao 结构体），方便测试时换成 mock。
- `main.go` 里在 `InitRouter()` **之前**调用 `database.InitDB()`：没有数据库整个服务没有意义，连不上就直接退出，不带病启动。

### 2.3 表结构：model/user.go

```go
type User struct {
	ID        uint      `gorm:"primaryKey" json:"id"`
	Username  string    `gorm:"size:64;uniqueIndex" json:"username"`
	Password  string    `gorm:"size:128" json:"-"`
	Nickname  string    `gorm:"size:64" json:"nickname"`
	CreatedAt time.Time `json:"created_at"`
	UpdatedAt time.Time `json:"updated_at"`
}
```

- GORM 默认把结构体名复数作为表名：`User` → `users`。
- 两套 tag 各管一头：`gorm:` 管数据库列，`json:` 管接口输出。
- **`json:"-"` 是关键**：Password 字段序列化时直接隐藏。接口返回 user 对象时不会把哈希泄露出去——敏感字段在 model 上一次性堵死，比在每个 handler 里记得"别返回密码"可靠得多。
- 建表用的是 `scripts/init.sql`（手写 SQL），和 model 保持对应；GORM 也提供 `AutoMigrate` 自动建表，生产项目一般还是用迁移脚本管理表结构。

### 2.4 数据库账号：不用 root

本项目的 MySQL 容器是共享的（还跑着别的项目），所以没有直接用 root，而是建了专用账号：

```sql
CREATE USER 'golang'@'%' IDENTIFIED BY 'golang123456';
GRANT ALL PRIVILEGES ON golang_study.* TO 'golang'@'%';
```

`golang` 账号只有 `golang_study` 这一个库的权限——就算应用层 SQL 被注入 `DROP DATABASE`，也删不掉别的库。这是实际项目的标准做法：**应用连库不用 root，权限只给到自己的库**。

## 三、登录链路逐层拆解

### 3.1 dao：查用户

```go
func GetUserByUsername(username string) (*model.User, error) {
	var user model.User
	err := database.DB.Where("username = ?", username).First(&user).Error
	if err != nil {
		return nil, err
	}
	return &user, nil
}
```

- `Where("username = ?", username)` 用占位符传参，**永远不要字符串拼接 SQL**（注入风险）。
- 查不到时 GORM 返回 `gorm.ErrRecordNotFound`，dao 原样上抛——"用户不存在对登录意味着什么"是 service 的解读，dao 不掺和。

### 3.2 service：业务逻辑

```go
var ErrInvalidCredentials = errors.New("用户名或密码错误")

func Login(username, password string) (*model.User, error) {
	user, err := dao.GetUserByUsername(username)
	if err != nil {
		if errors.Is(err, gorm.ErrRecordNotFound) {
			return nil, ErrInvalidCredentials
		}
		return nil, err
	}
	if err := bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(password)); err != nil {
		return nil, ErrInvalidCredentials
	}
	return user, nil
}
```

三个要点：

1. **业务错误定义为包级变量**（`ErrInvalidCredentials`），handler 用 `errors.Is` 识别它来决定响应 401，而不是靠字符串匹配错误消息。
2. **用户不存在和密码错误返回同一个错误**。如果分开提示"用户不存在"/"密码错误"，攻击者可以用报错差异探测哪些用户名注册过（用户名枚举）。
3. **比对错误用 `errors.Is` 而不是 `==`**：Go 的错误可能被包装过（`fmt.Errorf("%w")`），`==` 会漏判。

### 3.3 handler：参数与响应

```go
type loginRequest struct {
	Username string `json:"username" binding:"required"`
	Password string `json:"password" binding:"required"`
}

func (h *AuthHandler) Login(c *gin.Context) {
	var req loginRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		common.Fail(c, http.StatusBadRequest, "参数错误：username 和 password 必填")
		return
	}
	user, err := service.Login(req.Username, req.Password)
	if err != nil {
		if errors.Is(err, service.ErrInvalidCredentials) {
			common.Fail(c, http.StatusUnauthorized, err.Error())
			return
		}
		common.Fail(c, http.StatusInternalServerError, "服务器内部错误")
		return
	}
	common.Success(c, user)
}
```

- `binding:"required"` + `ShouldBindJSON` 一行完成参数校验，缺字段自动 400，不用手写 `if req.Username == ""`。
- handler 里**不出现任何业务判断和 SQL**，只做"翻译"：service 的三种结果 → 400/401/500 三种响应。
- `router/auth.go` 里改为 `auth.POST("/login", authHandler.Login)`——注册的是方法值，路由文件从此只管映射。

### 3.4 common：统一响应

```go
type Response struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data"`
}
```

所有接口统一返回 `{code, message, data}`，前端只需一套解析逻辑。学习阶段 `code` 直接复用 HTTP 状态码（200/400/401/500）；实际项目常用独立业务码（如 0 成功、1001 参数错误），把"传输层状态"和"业务状态"分开。

## 四、密码存储：bcrypt

数据库里存的不是明文，也不是 MD5/SHA256，而是 **bcrypt 哈希**（`$2a$10$...` 开头，60 字符，所以列宽 VARCHAR(128)）：

- **单向**：不可逆，泄露数据库也还原不出密码。
- **自带盐**：同一个密码每次生成的哈希都不同，彩虹表失效。
- **故意慢**（cost 因子，默认 10）：正常登录多花几十毫秒无感，暴力破解的成本指数级上升。MD5 太快，反而适合被穷举。
- 比对用 `bcrypt.CompareHashAndPassword(哈希, 明文)`，不是把明文再哈希一次用 `==` 比（虽然 bcrypt 下结果等价，但 API 语义更清晰，且能区分"哈希格式损坏"和"密码不对"）。

项目里没有 register 接口，插测试用户的哈希用小工具生成：

```bash
go run ./cmd/genhash 123456
# 输出: $2a$10$PB1X7gK5PrqG4bSxDPDz1e...
```

## 五、踩坑记录

1. **docker exec 导入 SQL 中文乱码**：`docker exec -i 容器 mysql ... < init.sql` 时客户端默认 latin1，UTF-8 中文被按 latin1 存成双重编码（HEX 出现 `C3A7...` 前缀）。必须加 `--default-character-set=utf8mb4`。
2. **`ON DUPLICATE KEY UPDATE` 只更新列出的列**：最初只 `UPDATE password = VALUES(password)`，重导后乱码的 nickname 没被修复——重复导入不会覆盖没列出的字段。
3. **共享容器 root@'%' 密码与 root@localhost 不同**：从宿主机连 Docker 里的 MySQL，来源 IP 是网桥地址（`172.17.0.1`），走的是 `root@'%'` 账号，和 `docker exec` 进去用的 `root@localhost` 可以是两个不同密码。解决方案是建专用账号而不是改 root。

## 六、验证

```bash
# 正确账号密码 → 200 + 用户信息（无 password 字段）
curl -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"123456"}'

# 错误密码 / 不存在的用户 → 401 + 用户名或密码错误（两者报错一致）
# 缺参数 → 400 + 参数错误
```
