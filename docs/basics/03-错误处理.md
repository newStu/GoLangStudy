# Go 笔记:错误处理(error)

> Go 没有 try/catch,错误就是一个普通的返回值。这篇笔记系统梳理 error 的核心机制:
> **error 是什么、怎么创建、怎么判断错误是谁、每一层该怎么处理**,还包括 panic 与
> defer/recover 的完整机制,最后结合本项目登录接口的
> `handler → service → dao` 三层链路看错误是怎么一层层"翻译"上去的。
>
> 配套代码:
> - `handler/auth_handler.go` —— handler 层:识别业务错误,翻译成 HTTP 状态码
> - `service/auth_service.go` —— service 层:哨兵错误 `ErrInvalidCredentials`,错误语义翻译
> - `dao/user_dao.go` —— dao 层:不认识业务,错误原样上抛

## 一、核心思想:error 只是一个值

Go 没有 try/catch 异常机制。在 Go 里,**错误就是一个普通的返回值**,最常用的多返回值写法就是"结果 + error":

```go
user, err := dao.GetUserByUsername(username)
```

`error` 本质是一个内置接口:

```go
type error interface {
    Error() string
}
```

任何实现了 `Error() string` 方法的类型都是 error。所以:

- `nil` 表示"没有错误"(成功)
- 非 `nil` 表示"出错了",此时通常应该忽略其他返回值

**`if err != nil` 是 Go 最核心的错误处理模式**,`dao/user_dao.go` 里写的就是最标准的形态:

```go
err := database.DB.Where("username = ?", username).First(&user).Error
if err != nil {
    return nil, err  // 处理不了就往上抛
}
return &user, nil    // 成功时显式返回 nil
```

这和 Java/Python 的"异常自动向上传播"完全不同——**Go 的错误必须手动一层层 return 回去**。
好处是每个函数的出口都看得见,坏处是代码显得啰嗦(这是 Go 社区公认的 trade-off)。

## 二、创建错误的三种方式

### 1. `errors.New` —— 固定文案的哨兵错误

`service/auth_service.go` 里用到了:

```go
var ErrInvalidCredentials = errors.New("用户名或密码错误")
```

注意它是一个**包级变量**,全局只有一份。这种"预先定义好、供调用方识别"的错误叫
**哨兵错误(sentinel error)**,按惯例命名以 `Err` 开头。

### 2. `fmt.Errorf` —— 带格式化的错误

```go
return nil, fmt.Errorf("查询用户 %s 失败: %w", username, err)
```

`%v` 只是拼接文字;**`%w` 会把底层错误"包"进去**,保留因果链,调用方可以用
`errors.Is` / `errors.As` 拆开检查。这是 Go 1.13 引入的错误包装机制。

### 3. 自定义错误类型 —— 需要携带更多数据时

```go
type ValidationError struct {
    Field   string
    Message string
}

func (e *ValidationError) Error() string {
    return e.Field + ": " + e.Message
}
```

当"一个字符串"不够用、调用方需要读取错误的附加字段时才需要它。当前项目还用不上,
知道有这个东西即可。

## 三、判断错误是谁:errors.Is 与 errors.As

### 本项目登录链路里实际发生了什么

```
dao:     数据库错误(gorm.ErrRecordNotFound 或连接失败等)
            ↓ 原样上抛
service: 识别 gorm.ErrRecordNotFound → 翻译成 ErrInvalidCredentials
         其他错误原样上抛
            ↓
handler: 识别 ErrInvalidCredentials → 返回 401
         其他错误 → 返回 500
```

`service/auth_service.go` 和 `handler/auth_handler.go` 用的是同一个工具:

```go
if errors.Is(err, gorm.ErrRecordNotFound) {
```

### 为什么用 `errors.Is` 而不是 `err ==`

```go
// ❌ 不推荐
if err == gorm.ErrRecordNotFound { ... }

// ✅ 推荐
if errors.Is(err, gorm.ErrRecordNotFound) { ... }
```

因为中间某层可能用 `fmt.Errorf("...: %w", err)` 把错误包了一层。`==` 只能匹配
"最外层那个错误对象",而 `errors.Is` 会**沿着包装链一层层往下找**。用 `==` 的话,
一旦有人包装了错误,判断就悄悄失效——这类 bug 很难查。

规则:**判断错误一律用 `errors.Is`**(错误没被包装时它和 `==` 等价,永远不吃亏)。

### `errors.As` —— 拆出具体类型

如果对方返回的是自定义错误类型(不只是哨兵值),用 `errors.As` 把它取出来:

```go
var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println("出错字段:", ve.Field)  // 能读取结构体字段
}
```

记忆方式:

- `errors.Is(err, 某个错误值)` → "错误链里**是不是**这个值"
- `errors.As(err, &某类型变量)` → "错误链里**有没有**这个类型,有就取出来"

## 四、每一层该怎么处理错误:三选一

每一层拿到 error 后,只有三种选择,本项目登录流程各层各占一种:

**1. 处理掉(终局)** —— handler 层做的:把错误翻译成 HTTP 状态码 + 响应体,然后 `return`。
到这就不再向上传了。

**2. 翻译后上抛** —— service 层做的:把 `gorm.ErrRecordNotFound`(技术性错误)翻译成
`ErrInvalidCredentials`(业务性错误)。**service 层的意义之一就是做这种"错误语义翻译"**,
让 handler 不需要认识 GORM。

**3. 原样上抛** —— dao 层做的:dao 不理解业务,只管把数据库错误交给懂业务的人。

一个容易忽略的细节:handler 对未知错误返回的是固定的 `"服务器内部错误"`,**没有把
`err.Error()` 返回给前端**——这是对的。错误详情可能泄露内部实现(表名、SQL、连接串),
只配打日志,不配给用户。可以在那里加一行:

```go
log.Printf("login error: %+v", err)
```

## 五、常见坑

**坑 1:变量遮蔽导致错误检查失效**

先明确作用域规则:`if` 语句可以带初始化语句(`if err := f(); err != nil`),
这个 err 是一个**新建的变量**,作用域是**整条 if/else 语句**(包括条件和所有分支),
出 if 就消失。而 `:=` 在哪个 `{}` 里,就在哪个作用域新建变量——所以它会"遮蔽"
外层的同名 err:

```go
user, err := dao.GetUserByUsername(username)  // 外层 err,函数剩余部分可见
if err != nil { ... }

if err := bcrypt.CompareHashAndPassword(...); err != nil {  // := 新建了一个 err,遮蔽外层
    return nil, err
}
fmt.Println(err)  // 这里还是外面那个 err,永远是 nil
```

对比三种写法:

```go
// 写法 1:if 内声明,作用域 = 整条 if 语句,出 if 就消失(官方推荐风格)
if err := f(); err != nil { ... }

// 写法 2:函数体声明,作用域 = 剩余整个函数
err := f()
if err != nil { ... }

// 写法 3:坑——if 里的 := 新建同名变量,和外层 err 是两个不同的变量
err := f1()
if err := f2(); err != nil { ... }
if err != nil { ... }  // 判断的还是 f1 的 err,和 f2 无关
```

`service/auth_service.go` 里 `if err := ...` 的写法没问题(错误在 if 块内就处理掉了),
而且作用域最小化正是 Go 推荐它的原因——出 if 就消失,后面不会残留一个值不确定的旧 err。

for 循环里有同款问题(循环体也是一个块作用域):

```go
var err error
for _, u := range users {
    if err := save(u); err != nil {  // 同样是新变量,遮蔽外层 err
        continue
    }
}
return err  // 永远是 nil,save 的错误全丢了
```

一句话总结:**`{}`(含 if / for 的初始化语句)每出现一次就是一个新的作用域**;
只要记得"if 里的 err 是新变量、出了块就不存在",这种写法只有好处没有坑。

**坑 2:忘了 return**

```go
if err != nil {
    common.Fail(c, ...)
    // 忘了 return!代码会继续往下走,可能对 nil user 解引用 → panic
}
```

Go 编译器不会替你检查这个。handler 里每处都记得 `return`,很好。

**坑 3:吞掉错误**

```go
if err != nil {
    _ = err  // 或者干脆不管,错误无声无息消失,排查问题时痛苦万分
}
```

不想处理至少打条日志。**错误可以被翻译、可以被打日志,但不应该被无声丢弃。**

**坑 4:在循环里丢弃错误**

```go
for _, u := range users {
    if err := save(u); err != nil {
        continue  // 静默跳过,最后只返回 "成功",调用方根本不知道丢了几条
    }
}
```

需要的话用 `errors.Join(err1, err2, ...)`(Go 1.20+)把多个错误合并成一个返回。

## 六、panic:另一半的错误处理

前面说的 error 是"温和"的错误——调用方拿到后自己决定怎么办。Go 还有另一套机制
**panic(恐慌)**:它不是返回值,而是**一条会沿着调用栈向上炸的失控信号**。

### 1. panic 是什么

```go
func mustPositive(n int) int {
    if n <= 0 {
        panic("n 必须是正数")  // panic 接收任意类型参数,通常是 string 或 error
    }
    return n
}

func main() {
    fmt.Println(mustPositive(-1))  // panic: n 必须是正数
    fmt.Println("这行永远执行不到")  // panic 之后的代码不再执行
}
```

panic 一旦发生:

- 当前函数**立即停止**,后面的代码一行都不执行;
- 信号沿着调用链向上传播(`mustPositive` → `main` → 程序退出),**上层调用者也没法用
  `if` 捕获它**——这一点和 error 完全不同;
- 退出前会打印 goroutine 堆栈,从 panic 的那行一直列到 `main`,排查问题时非常有用。

除了自己主动 `panic(...)`,很多常见 bug 也会触发**运行时 panic**:

```go
nums := []int{1, 2, 3}
_ = nums[5]          // panic: index out of range [5] with length 3

var m map[string]int
m["a"] = 1           // panic: assignment to entry in nil map(忘了 make)

var p *int
*p = 10              // panic: invalid memory address or nil pointer dereference
```

### 2. defer + recover:接住 panic 的唯一方式

panic 沿调用栈向上炸的过程中,**每一层的 `defer` 都会执行**。而接住 panic 的唯一方式,
是在 defer 里调用内置函数 `recover`:

```go
func safeCall() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("接住了 panic:", r)
        }
    }()
    panic("出大事了")
    // recover 后 safeCall 正常返回,panic 不会继续向上炸
}

func main() {
    safeCall()
    fmt.Println("main 继续运行")  // 会执行
}
```

三条硬规则:

- **recover 只有在 defer 的函数里直接调用才有效**。写在普通代码里永远返回 `nil`;
- recover 之后,panic 就被"消化"了,当前函数正常返回给调用方;
- `recover` 拿到的是 `panic(...)` 时传的那个值(`interface{}` 类型),所以常配合
  `fmt.Sprintf("%v", r)` 打日志。

### 3. 跨 goroutine:recover 救不了别的协程

这是最容易踩的坑:**panic 只能在它发生的那个 goroutine 里被 recover**。
主 goroutine 里的 recover 接不住子 goroutine 的 panic:

```go
func main() {
    defer func() { recover() }()  // ❌ 接不住下面的 panic

    go func() {
        panic("子协程炸了")  // 没人 recover → 整个进程崩溃
    }()

    time.Sleep(time.Second)
}
```

任何一个 goroutine panic 且未被 recover,**整个进程直接退出**,其他还在干活的协程
全部陪葬。所以"每个新起的 goroutine,要么保证里面不会 panic,要么自己套一层
recover"是并发代码的纪律。

正确做法就一条原则:**recover 必须写在发生 panic 的那个 goroutine 自己的 defer 里**:

```go
// worker 在子协程里干活,panic 由子协程【自己】的 defer recover 接住
func worker(name string) {
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("接住 %s 的 panic: %v\n", name, r)
		}
	}()

	fmt.Printf("%s 开始干活\n", name)
	if name == "Tom" {
		panic("Tom 的任务写错了,炸了")
	}
	fmt.Printf("%s 干完了\n", name)
}

func main() {
	go worker("Alice") // 正常完成
	go worker("Tom")   // 内部 panic,但被自己的 recover 接住
	go worker("Bob")   // 正常完成

	time.Sleep(time.Second)
	fmt.Println("三个协程都结束了,进程安然无恙")
}
```

关键点:`defer func() { recover() }()` 写在 **worker 函数体内**——worker 被 `go` 起来后,
这个 defer 就属于那个子协程,所以 panic 在哪发生,recover 就在哪候着。

实际项目里更常见的封装是写一个"安全起协程"的工具函数,免得每个 `go` 都手写一遍 defer:

```go
// SafeGo 统一封装:起协程 + 内置 recover,避免某个协程 panic 拖垮整个进程
func SafeGo(name string, fn func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				log.Printf("goroutine [%s] panic: %v\n%s", name, r, debug.Stack())
			}
		}()
		fn()
	}()
}

// 用法
SafeGo("订单超时检查", func() { checkOrderTimeout() })
```

注意 recover 之后协程里的后续代码不会执行(协程直接结束),所以它保护的是**进程**,
不是**这个协程的任务**——任务本身还是失败了,只是不连累别人。这也再次说明:
能预期到的失败应该用 error 返回,panic/recover 只是最后的保命手段。

### 4. Web 项目里的 panic:Gin 的 Recovery 中间件

HTTP handler 是框架替我们起的调用入口,如果 handler 里 panic 了怎么办?Gin 内置了
**Recovery 中间件**,本质上就是在每个请求外面包了上面那套 `defer + recover`:

```
请求 → gin engine → Recovery 中间件(defer + recover) → 我们的 handler
                                                    ↓ panic!
         ← 接住,记录堆栈日志,返回 500 ← ────────┘
```

效果:单个请求里 panic 只会让**这个请求**返回 500,**进程不挂**,其他请求照常服务。
`gin.Default()` 就默认带 Logger + Recovery;如果用 `gin.New()` 就要自己挂:

```go
r := gin.New()
r.Use(gin.Logger(), gin.Recovery())
```

### 5. error vs panic:怎么选

| | `error`(返回值) | `panic`(崩溃) |
|---|---|---|
| 语义 | **可以预期**的失败:用户输错密码、查无记录、网络超时 | **不该发生**的程序性错误:数组越界、空指针、程序员写错了代码 |
| 传播方式 | 手动一层层 `return` | 自动沿调用栈向上炸,defer 依次执行 |
| 捕获方式 | `if err != nil` | 只能 `defer` + `recover` |
| 谁处理 | 调用方逐层决定 | 不 recover 就崩掉整个进程 |
| Web 场景 | 参数错误、业务失败 → 返回 4xx/5xx | Gin Recovery 接住 → 该请求返回 500,进程不挂 |

判断标准就一句话:**调用方有没有可能合理地处理这个失败?**

- 用户密码输错,调用方能处理(提示重输)→ error;
- 数据库连不上,调用方能处理(降级、重试)→ error;
- `nums[5]` 越界,说明代码写错了,任何调用方都处理不了 → panic 是合理结果
  (或直接修好代码);
- `regexp.MustCompile(写死的正则)` 在程序启动时校验一次,错了就是开发者的问题,
  启动时 panic 比带病运行更安全——这类"初始化期检查"是标准库里 panic 的典型用法。

规则:**业务里一切"可能的失败"都用 error 返回,panic 只留给 bug 和启动期检查**。
本项目全部用 error 是正确的姿势,基本不需要手写 panic/recover
(Gin 框架内部已经帮我们 recover 了)。

```
用户输错密码
  ↓ bcrypt.CompareHashAndPassword 返回 err
service: return nil, ErrInvalidCredentials        ← 哨兵错误
  ↓
handler: errors.Is(err, service.ErrInvalidCredentials) 为 true
  ↓
common.Fail(c, 401, "用户名或密码错误")            ← 终局:翻译成 HTTP 响应

用户不存在
  ↓ dao 返回 gorm.ErrRecordNotFound
service: errors.Is 判定后翻译成 ErrInvalidCredentials  ← 错误翻译
  ↓ (走同上路径,对外报错一致,防枚举用户名)

  ↓ dao 原样上抛 → service 原样上抛(不认识的错误不翻译)
handler: 不认识 → 兜底 500 "服务器内部错误"         ← 兜底策略
```
